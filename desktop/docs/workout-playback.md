# Workout playback and BLE ERG

Exact playback plans come from the account API, introduced by [web PR #95](https://github.com/flaviendelangle/undertrained/pull/95). The server validates and expands the same workout definitions used by the website. It resolves relative targets against the rider's current FTP and preserves fixed watts, ramp endpoints, free steps, cadence and notes. Old servers remain compatible, but their chart previews cannot drive playback.

The player uses the recording's active monotonic clock. Pauses freeze the workout, while skipping adds an offset only to the workout timeline. Ramps interpolate linearly. Intensity scales targets between 50% and 150%, then rounds to 5 W and clamps to 0–1000 W, matching the website. The display and ERG transport use that same resolved target. Completing the plan leaves the recorder running for a free cool-down until the rider finishes.

FTP tests expose their timed steps. Automatic ramp-exhaustion detection, FTP estimation and account FTP updates are not included. Recorded FIT files contain measured values; target compliance and workout targets are not exported yet.

## Trainer control

ERG requires an explicitly enabled, connected trainer that confirmed target power: a Bluetooth FTMS trainer advertising power-target support, a writable/indicating control point and a valid Supported Power Range, or an ANT+ FE-C trainer whose FE capabilities page (54) sets the target power bit. Unsupported trainers, power meters and heart-rate-only rides can follow the targets manually. Every command names the trainer it is for and goes to that trainer's radio.

The implementation follows the [Bluetooth Fitness Machine Service specification](https://www.bluetooth.com/specifications/specs/fitness-machine-service-1-0-1/) and the website's command sequence: Request Control, Start/Resume, Set Target Power. Only an explicit “Start not supported” response is tolerated. Writes are serialized and await matching control-point indications. Changing ramp targets are coalesced so the trainer does not execute a backlog. Commands are bound to the selected device id and dispatched separately from discovery and pairing, so a slow heart-rate connection cannot block a trainer release. Targets outside its advertised range or increment are rejected, never silently changed to another value.

Over ANT+, the trainer is asked for page 54 when it is chosen and counts as connected once it answered (three requests, three seconds apart; silence means read-only). Targets go out as page 49 (quarter watts) and releases as page 51 at 0 % grade with a 0.004 rolling resistance, as the website does: FE-C target power is sticky, so a 0 W target would keep the trainer in ERG at zero watts. A trainer without simulation mode is released into basic resistance at 0 % (page 48) instead, and one with neither mode never counts as taking ERG. The scan channel cannot transmit, so commands are extended acknowledged messages naming the trainer, queued on a second channel the stick sends after the trainer's next broadcast (a stick that refuses extended messages gets plain acknowledged data on that channel, assigned to the trainer's ID). The trainer's acknowledgement is its answer. One that went unheard (EVENT_TRANSFER_TX_FAILED) is sent again, at most five times in all; a refusal by the stick is final. A command waits for the trainer's next broadcast, so it rides out the four-to-five-second dropouts an ANT+ link shows several times an hour; one with no outcome within ten seconds clears the channel so it cannot reach the trainer later, and control stays off until the trainer is chosen again, like a Bluetooth timeout. Since nothing disconnects an ANT+ trainer, a release still goes out once if a target was held, or if an unacknowledged attempt of the lost target may have reached the trainer. Letting the trainer go cancels a target still out, clearing the channel, and releases any target the trainer may hold, waiting up to five seconds for the release to be acknowledged. See [the ANT+ transport](ant-bridge.md).

Pause, free steps, completion, disabling ERG and finishing request a release (Reset over Bluetooth). Closing a connection attempts release before disconnecting. Release failure causes disconnection; the app cannot promise what resistance a disconnected trainer's firmware chooses. A command timeout invalidates the link because FTMS indications have no transaction id: a late response must not acknowledge a later command. Reconnect before enabling ERG again. Control is never enabled merely because a sensor connects. The rider may switch it on before the ride, on the ready screen; the choice applies when the recording starts, under the same checks as the switch during the ride. That choice is saved with the app's settings and shown again on the next ready screens, but only while a guided workout and a trainer that takes control are there; switching during a ride, or the app switching control off after a failure, never changes it. The ride reads live power and the last valid power report through the sensor module's reading interface, shared by both radios. Fifteen seconds without any trainer power reading also disables ERG and requests release, while recording continues; shorter dropouts, which ANT+ links show several times an hour, leave it on. A real zero-watt reading remains valid; enabling requires a fresh power reading.

## Compatibility

Detection uses services, feature flags, the power range and the FE capabilities page, never a brand-name allowlist. Elite documents both Bluetooth FTMS and ANT+ FE-C for the [Suito-T](https://www.elite-it.com/uploads/product/catalog_box_cta_file_en/188/SUITO-T_FU_2025_EN.pdf), the owner's likely trainer. Its support makes it a candidate for both paths, not a hardware-verified device. Other brands exposing the same standard can use the same path. Older trainers exposing only proprietary control services need separate adapters; advertising Cycling Power alone does not imply resistance control.

## Validation

Pure player tests cover ramp interpolation, boundaries, missing versus zero targets, intensity limits, skipped steps and malformed plans. A checked-in fixture generated with the website at commit `d10fbbc` checks 96 snapshots across both built-in workouts and four intensity settings against the website's resolver. Mock transport tests cover acknowledgement order, cancellation during control acquisition, release and rejected control without automatic retry; over ANT+, a fake stick covers the capability request, the fallback from extended messages, coalescing, the bounded resend of unheard commands, the release after a failure, timeouts and letting the trainer go. The ride module's tests cover the control's place in the ride: a short dropout leaving it on and fifteen seconds without power switching it off with one release, stale answers ignored, a refusal releasing once with no retry, enabling refused without a fresh reading, a replaced trainer released and forgotten with nothing sent to the next one, and request numbers that go on across rides. UI smoke tests cover the actual ride controls without writing to hardware.

BLE ERG still needs validation with a physical trainer. Unit tests and successful builds do not establish hardware compatibility. No test or development launch automatically sends a resistance command.
